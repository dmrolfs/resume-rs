# rsm-141.23.3: analysis so far

Date: 2026-11-21. Worktree `../resume-4`, branch `work/rsm-141.23.3` from `origin/main` f9fadb5. No code written yet.

## 1. Functional intent

Selection only keeps or drops items; it never changes their order, so one baseline resume shows every role's bullets in one fixed order. A reader gives a role's first bullets the most attention. A leadership posting wants leadership bullets first in each role; a technical posting wants the baseline order. Today the only way to get both is to clone and hand-edit the baseline per audience, which forks it. The owner's "Org Leader" draft reorders the shared bullets of 4 of 9 roles.

This bead lets a position spec or profile carry an ordered `promote = ["tag", ...]` list in `[select]`. At build time, tagged items rise within their own container (stable, never across containers), and the build summary names what moved. One baseline then yields both orders, and the order is reproducible from the spec.

Sources read beyond the bead: epic rsm-141.23 (description, notes, open questions), `rsm-141.22_tailoring-decisions.md` Addendum 1 D2 and Addendum 2, `rsm-141.22.3_merged-baseline-probe.md`.

## 3. Where the analysis disagrees with the bead

1. **Paragraphs.** The epic records an owner decision: "bullets and paragraphs". The analysis recommends bullets only (prose order is meaning; enabling paragraphs later would change existing specs). Needs the owner.
2. **"A parent bullet's children".** The container does not exist in the model. Strike the clause.
3. **"One tag each reproduces CDK, Rightside, Accenture exactly."** True only for the bullets both drafts share. Matching the draft's slots for its leader-only (`#lead`) bullets needs CDK 2, Rightside 3, and the HERE AI-and-data-platforms era 3 (not one of the four). The "four draft orders" test must say which it pins.
4. **Tags select and rank.** A promote tag on an untagged bullet makes it tagged, and a tag selection that omits that tag drops it. Ordering must stay orthogonal to selection, be documented, and be pinned by a test.
5. **Placement.** The bead says "a pure `order(Resume, &[Tag]) -> Resume` after select". That relies on every caller remembering the step. Recommended: `promote` on `Selection`, applied inside the walk, with the arithmetic in a pure `select::order` module.
6. **Estimate.** 1 to 1.5 days, not 0.5.
7. **Acceptance tests that need `--spec`.** "build --spec twice is byte-identical" and the guide worked example depend on rsm-141.23.2. Prove determinism here through `to_selection()` and `Session::assess` twice with a negative control, and leave the CLI test and guide section to rsm-141.23.2.

## 4. Recommended design (from the oracle analysis)

- `Selection.promote: Vec<Tag>`; `to_selection()` copies it; the compiler forces the two construction sites.
- Domain: each `Bullets` list (section or role) and each era's items. Paragraphs, blurb, roles, eras, page breaks are fixed anchors. Blocks are never merged or split.
- Rank: place in `promote` of the first promote tag among inherited and own tags; none ranks last; a group ranks by its wordings' union tags. Stable sort. A role-level promote tag caps ranks below it.
- Report: `SelectionReport.reordered: Vec<Reordered>` (container, kept count, items that rose with baseline node and from/to positions). "Moved" means rose.
- Summary: `promote ...` in the selection line; one line per reordered list; `moved up: nothing` when promote is set and nothing rose. JSON adds `promote` and `reordered`. `is_silent` stays true for an empty promote.
- Unknown promote tag: reuse `unknown-tag`, a separate diagnostic prefixed `promote`.
- Tests: pure unit and proptest in `order.rs`; behavior and report in `src/select/tests.rs`; properties in `tests/select_property_test.rs` (permutation per container, empty is identity, idempotent, equal rank keeps order, nothing crosses a container, containers keep order); draft-shaped fixtures in a new `tests/ordering_test.rs`; determinism through `Session::assess`.
- Full detail, signatures, exact summary text, C4 diagrams: `history/rsm-141.23.3_oracle-analysis-and-plan.md`.

### Points of the analysis that still hold

### Point re-weighed: paragraphs

The analysis recommended bullets only, against a recorded owner decision (epic rsm-141.23, 2026-11-20: "bullets and paragraphs").
Its two arguments are weaker than stated.
"Prose order is meaning" is the author's call, and no paragraph moves unless the author tags it and lists the tag.
"Enabling paragraphs later would change existing specs" argues for deciding now, not for leaving them out.
The machinery objection (mixing kinds rebuilds blocks) does not apply to a smaller rule: a run of adjacent paragraphs in one container is its own list, sorted by the same rank, never mixed with bullets.
That keeps every block boundary, costs one more call site per container, and honours the owner decision.
The blurb, and a chosen blurb wording that takes the blurb's place, never move.
No evidence needs paragraph ordering (the four roles are all bullets), so bullets only remains a valid choice if the owner prefers it.

### Decisions now

- Open for the owner: paragraphs (run-of-paragraphs rule, or bullets only).
- Taken as defaults unless the owner objects: strike "a parent bullet's children"; pin both shared-only and full draft orders; rank tags also select, documented and tested; unknown promote tag warns from a spec and is a note from a profile, as 141.23.2 does for tags.

### Q1. Paragraphs orderable, or bullets only?

Recommendation: bullets only. Confidence: high.
- In both drafts, no container holds two paragraphs. Each section or role has at most one: the Summary intro and the role blurbs (a role's blurb is its own field and never moves under any proposal). The run-of-paragraphs rule from Addendum 1 would never move anything in the owner's content.
- The one mixed container, Summary (a paragraph, then bullets), keeps its paragraph first in both drafts, so mixing kinds is not wanted either.
- Letters already fix paragraph order as authored (`ref/Cover-Letters-Analysis.md:283`), so bullets-only keeps one rule: prose keeps its order, lists can be reordered.
- The "decide now or specs change later" argument from Addendum 1 does not hold: adding paragraph runs later changes output only for a spec that promotes a tag carried by one of two adjacent paragraphs, and no such content exists.
- This narrows the owner's 2026-11-20 epic note ("bullets and paragraphs"). That note was written before any container was checked; it needs the owner's confirmation, and the epic note must be updated.
Addendum 1's lean toward paragraph runs is withdrawn.

### Q2. Strike "a parent bullet's children"?

Recommendation: strike it, and document that a flattened child orders as a sibling. Confidence: high.
- `Bullet` has no children (`src/model/mod.rs:110-116`); the parser flattens nested lists with a `nested-list` warning (`src/markdown/blocks.rs:822`).
- Neither draft has a nested bullet.
- Keeping children would need a model and schema change with no case that calls for it.

### Q3. What the four-draft-orders test pins

Recommendation: pin the full Org Leader order, with leader-only bullets placed as above, for the four roles (pipeline era with 4 rank tags; CDK, Rightside, Accenture with 1). Add the AI era as a zero-tag case (leader-only bullets placed, no promote needed). Drop the separate shared-only fixtures. Confidence: high.
- The full order is what a reader of the leader build sees, and it is the order the owner wrote by hand.
- The shared-only order is a subsequence of the full one, so it adds no check.
- Each fixture keeps its negative control: with `promote` empty, the baseline order comes out.

### Q4. Rank tags also select

Recommendation: keep ordering separate from selection; document and test it; do not change `judge`. Confidence: high.
- The case is real, not theoretical. Three general bullets need a rank tag: two in the pipeline era (u1 and u2 in the oracle's table) and one in Accenture (u5). All three appear in both drafts. Today they are untagged, so both builds keep them.
- Give one a rank tag such as `#people` and an architect build with `tags = ["arch"]` drops it (`TagsNotSelected`, `src/select/rules.rs:70-79`).
- The author's remedy is one more tag on that bullet (`#people #arch`), or `people` in the architect spec's `tags`. The summary already lists the drop with its reason, so the mistake shows on the first build.
- The alternatives are worse. Counting promote tags as selected turns an order list into a filter. Ignoring promote tags in "untagged" makes whether a bullet is kept depend on another list in the spec, and breaks the rule that a tag on a bullet means an audience.
- The guide sentence: "A tag you add only to rank a bullet also counts for selection: if the bullet was general, tag it for every audience that keeps it."

### Q5. The `--spec` twice-identical test and the guide example

Recommendation: both in this bead. Confidence: high.
- `build --spec` landed (e35b5e2) and the guide section is written (`docs/User-Guide.md:844-1026`), so the reason to hand them off is gone.
- This bead must remove `Error::PromoteNotApplied` anyway, and its four tests and guide row (`docs/User-Guide.md:952`) turn into the promote tests and the guide subsection.

### Q6. Unknown promote tag: warning or error?

Recommendation: warning when the spec wrote it, note when only a profile did, through `NameOrigins` like tags and wordings. Confidence: high.
- It is the rule the owner approved for 141.23.2 (origin-split severity), so a promote typo behaves like a tag typo.
- An error is right for picks because a pick asks for exact text. A promote typo moves nothing and changes no text, and the summary's `moved up: nothing` shows it.
- A profile is shared across baselines that use different tags, so an error there would block valid builds.
